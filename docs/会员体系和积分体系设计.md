# 会员体系和积分体系

> 版本：v2.0（代码现状，2026-07-30）
>
> 本文以当前代码、数据库初始化脚本和 API 文档为准，用于说明已经存在的行为。尚未实现或存在缺陷的内容单独标注，不把规划接口当成现有接口。

## 1. 当前结论

会员和积分是两套独立体系：

- 会员只有一种有效身份：VIP。套餐可以是月度、季度、年度，但当前权限判断只区分“有有效会员”和“无有效会员”。
- 会员通过 `config_membership_package` 配置价格、有效天数和权益；支付订单使用 `payment_order`，开通记录使用 `user_membership`。
- 积分是永久有效的整数余额，余额和流水都从 `user_points` 的最新记录计算，不支持提现、转账或前端直接修改。
- 积分可兑换数据库中已上架的商品/权益。兑换会在同一事务中扣分、创建兑换订单并扣减库存；只有已映射的额度商品会自动发放额外次数，其它商品进入待履约状态。
- 申请、浏览、爆灯和纸飞机使用日额度；积分兑换的额外次数记录在 `user_quota_grant`，消费记录写入 `user_quota_usage`。

会员不能绕过手机号绑定、资料完整度、实名认证、隐私设置、拉黑关系、账号停用和内容安全规则。

## 2. 会员体系

### 2.1 套餐配置

在售套餐来自 `config_membership_package` 中 `is_active=1` 的记录，按 `sort,id` 排序。数据库初始化约定的套餐编码为：

| 编码 | 用途 |
| --- | --- |
| `monthly` | 月度会员 |
| `quarterly` | 季度会员 |
| `yearly` | 年度会员 |

服务端返回以下字段：`code`、`name`、`duration_days`、`price`、`original_price`、`daily_price`、`badge`、`rights`。有效期使用数据库的 `duration_days`，不接受前端传入的会员天数或到期时间。

价格可以由环境变量覆盖，未配置时回退到数据库：

- `MEMBERSHIP_MONTHLY_PRICE`、`MEMBERSHIP_QUARTERLY_PRICE`、`MEMBERSHIP_YEARLY_PRICE`
- 对应的 `_ORIGINAL_PRICE`、`_DAILY_PRICE`

### 2.2 有效会员判断

会员状态查询和额度服务均按以下条件判断有效会员：

```sql
status = 1
AND (start_at IS NULL OR start_at <= UTC_TIMESTAMP())
AND (end_at IS NULL OR end_at > UTC_TIMESTAMP())
```

当前会员状态响应为：

```json
{
  "is_vip": true,
  "package_type": "quarterly",
  "start_at": "2026-07-30T00:00:00",
  "end_at": "2026-10-28T00:00:00",
  "rights": {}
}
```

无有效会员时 `is_vip=false`、`package_type/start_at/end_at` 为 `null`，`rights` 仍返回默认权益结构。

会员记录字段为：`user_id`、`package_type`、`amount`、`order_no`、`start_at`、`end_at`、`status`。代码实际使用的状态含义是：`1` 生效中、`2` 已过期、`3` 已退款；数据库注释没有实现待生效状态流转。

### 2.3 当前权益和额度

当前代码的默认权限基线如下；会员套餐中的 `rights` 可以提供 `apply_bonus`，但 VIP 的申请额度仍是基础额度加该 bonus：

| 项目 | 普通用户 | VIP |
| --- | ---: | ---: |
| 每日申请认识 `apply` | `APPLY_DAILY_FREE_LIMIT`，默认 3 | 基础额度加 `rights.apply_bonus`，默认 3 |
| 每日爆灯 `superlike` | `SUPERLIKE_DAILY_FREE_LIMIT`，默认 1 | `SUPERLIKE_DAILY_VIP_LIMIT`，默认 3 |
| 每日完整资料浏览 `browse` | `BROWSE_DAILY_LIMIT`，默认 8 | 20 |
| 高匹配浏览额外次数 | `BROWSE_HIGH_MATCH_BONUS`，默认 5 | 按发现服务逻辑处理 |
| 纸飞机 `paper_plane` | `PAPER_PLANE_DAILY_LIMIT`，默认 3 | 默认仍为 3 |
| 浏览历史 | 仅当天 | 全部历史 |
| 访客详情 | 不可查看详细名片 | 可查看访客名片 |

`GET /users/me/quotas` 返回每项的 `quota_code`、`daily_limit`、`daily_used`、`daily_remaining`、`extra_remaining`、`total_remaining`。日额度使用 Redis 日键；积分兑换的额外额度从 `user_quota_grant` 汇总，过期的 grant 不计入余额。

会员只影响上述权益和 VIP 可见性，不会绕过目标用户隐私、拉黑、封禁、实名和资料门槛。所谓“浏览不限”也不表示绕过 Redis、频控或安全校验。

### 2.4 会员接口

接口前缀为 `/api/v1`：

| 方法 | URL | 权限 | 当前行为 |
| --- | --- | --- | --- |
| `GET` | `/membership/packages` | 无 | 查询上架套餐 |
| `GET` | `/users/me/membership` | 登录 | 查询当前有效会员和权益 |
| `GET` | `/users/me/membership/history?page=1&page_size=20` | 登录 | 查询本人会员历史，页大小 1~50 |
| `POST` | `/membership/orders` | 登录 | 创建微信待支付订单，必须带 `Idempotency-Key`，有效长度 1~128 |
| `GET` | `/membership/orders/{order_no}` | 订单本人 | 查询本人订单 |
| `POST` | `/payments/wechat/callback` | 支付服务端 | 处理微信回调；当前没有真实验签实现 |

创建订单时服务端按套餐编码查询上架数据并使用服务端价格，创建 `VIP` 前缀订单号，订单有效期为创建后 30 分钟，支付方式固定为微信（`pay_type=1`）。同一用户使用同一幂等键会返回已有订单。

当前支付回调行为：

- `WECHAT_PAYMENT_MODE=mock`：允许进入 mock 开通逻辑，重复处理已支付订单直接返回。
- `WECHAT_PAYMENT_MODE=real`：当前固定返回 `503`，真实微信 API v3 验签尚未接入。
- mock 回调会锁定支付订单，校验订单状态后更新支付状态并新增一条 `user_membership`，会员有效期从当前时间起按套餐天数计算。

已知实现问题：创建支付订单时 `payment_order.product_type` 当前写入的是数值 `1`，回调按套餐编码与 `config_membership_package.code` 关联；因此 mock 回调可能无法找到套餐并开通会员。完成真实支付前必须修复该字段并补充回调、续费、退款和并发测试。

## 3. 积分体系

### 3.1 账本和余额

`user_points` 是当前唯一积分账本，字段为：

| 字段 | 含义 |
| --- | --- |
| `user_id` | 用户 |
| `type` | `1` 签到、`2` 任务、`3` 邀请、`4` 兑换消费 |
| `amount` | 本次变动，收入为正、消费为负 |
| `balance` | 本次变动后的余额 |
| `desc` | 变动原因 |
| `created_at` | 创建时间 |

当前余额取该用户最新一条流水的 `balance`；累计获得和累计扣减分别汇总正数和负数。收入和消费均写流水，消费前会锁定最新余额并检查余额是否足够，余额不足返回 `409`，不会产生负余额。

积分没有过期字段和批次模型，因此当前按永久有效处理。代码尚未实现冻结、过期、冲正、积分账户表或积分批次。

### 3.2 积分获取

当前真正开放的入口：

| 编码/类型 | 条件 | 默认值 | 幂等依据 |
| --- | --- | ---: | --- |
| `checkin` / type `1` | 每日首次签到 | 5 | `user_checkin(user_id, checkin_date)` 唯一键 |
| `profile_complete` / type `2` | 资料完成度达到 100% 后领取 | 50 | `user_task(user_id, task_code)` |
| `realname_verified` / type `2` | `realname_status=2` 后领取 | 100 | `user_task(user_id, task_code)` |

奖励可以通过以下环境变量覆盖：`POINT_CHECKIN_REWARD`、`POINT_PROFILE_COMPLETE_REWARD`、`POINT_REALNAME_VERIFIED_REWARD`。

任务接口只暴露 `profile_complete` 和 `realname_verified` 两项；已领取任务再次领取时返回 `claimed=true`、`points=0`，不会重复入账。

邀请记录 `invite_record` 支持 `0 已邀请、1 已注册、2 已实名、3 已奖励` 等状态字段，当前积分服务只提供邀请记录查询，注册/实名事件推进及邀请积分自动入账尚未接入。

### 3.3 积分消费和额外额度

积分商品来自 `config_point_product` 中 `is_active=1` 的记录，字段包括 `code`、`name`、`product_type`、`points_cost`、`value`、`stock`。`product_type` 由数据库配置，通常为 `goods` 或 `right`。

支持通过 `POINT_COST_<商品编码>` 覆盖商品的积分价格；库存、上下架和权益值仍以数据库为准。当前服务层会把以下商品编码映射为额外额度：

| 商品编码 | 额度编码 | 发放数量 |
| --- | --- | --- |
| `extra_apply` | `apply` | 商品 `value`，最少 1 |
| `browse_unlock` | `browse` | 商品 `value`，最少 1 |
| `paper_plane_unlock` | `paper_plane` | 商品 `value`，最少 1 |

其它商品仍会扣分并创建兑换订单，但不会由当前服务自动发放额度，需后台履约处理。数据库可能存在 `profile_detail_unlock` 等配置，但当前代码没有对应权益映射，不能视为已生效能力。

### 3.4 兑换事务和幂等

兑换接口：

```http
POST /api/v1/users/me/points/redeem
Idempotency-Key: <1~128 字符>
Content-Type: application/json

{"product_code":"extra_apply"}
```

服务端在一个数据库事务中执行：

1. 按用户和幂等键查询已有兑换订单；已有订单直接返回，不重复扣分。
2. 锁定已上架商品，校验库存。
3. 锁定用户最新积分余额，校验余额并计算扣减后的余额。
4. 写入负数 `user_points` 流水。
5. 创建 `point_redeem_order`。
6. 对已映射的权益写入 `user_quota_grant`；有库存限制时扣减库存。

`point_redeem_order.status` 当前使用：`0` 待履约、`1` 已自动发放/已完成。订单表通过 `(user_id, idempotency_key)` 唯一约束防止重复兑换。兑换请求缺少幂等键、商品不存在、库存不足、余额不足和权益数量配置无效时分别返回 `422`、`404`、`409` 或 `422`。

当前没有积分兑换订单列表/详情接口，也没有取消、退款、冲正、实物发货或人工履约接口。兑换失败时事务回滚，已成功扣分的订单不能通过现有接口主动退款。

当前已使用的核心表：

## 6. 接口输入输出契约

### 6.1 通用约定

- API 前缀为 `/api/v1`。
- 除套餐列表、积分商品列表外，其余接口均需要 `Authorization: Bearer <access_token>`。
- 请求和成功响应使用 `Content-Type: application/json`；支付回调也使用 JSON。
- 时间字段为 ISO 8601 日期时间字符串，服务端使用 UTC 数据库时间；前端不得自行计算会员是否有效。
- 分页接口的 `page` 默认 `1`，`page_size` 默认 `20`，最大 `50`。
- 业务错误沿用 FastAPI 默认结构：`{"detail":"错误说明"}`。鉴权失败、参数校验失败和业务冲突不返回数据库 SQL 或堆栈。

### 6.5 创建会员支付订单

```http
POST /api/v1/membership/orders
Authorization: Bearer <access_token>
Idempotency-Key: membership-user-1001-quarterly-20260730
Content-Type: application/json

{
  "package_code": "quarterly"
}
```

成功响应 `200`：

```json
{
  "order_no": "VIP20260730083000A1B2C3D4E5",
  "package_code": "quarterly",
  "product_name": "季度会员",
  "amount": 79.9,
  "pay_type": 1,
  "status": 0,
  "expire_at": "2026-07-30T09:00:00",
  "payment_required": true
}
```

字段说明：`status=0` 表示待支付，`pay_type=1` 表示微信支付，`payment_required=true` 表示仍需支付。相同用户重复使用同一个幂等键，会返回同一订单，不会新建订单。

请求校验和错误示例：

| 状态码 | 条件 | 示例 |
| ---: | --- | --- |
| `401` | 未登录或 Token 无效 | `{"detail":"Not authenticated"}` |
| `404` | 套餐不存在或已下架 | `{"detail":"Membership package not found"}` |
| `422` | 缺少幂等键、长度超过 128 或套餐编码为空 | `{"detail":"Idempotency-Key is required"}` |

### 6.7 微信支付回调

```http
POST /api/v1/payments/wechat/callback

{
  "order_no": "VIP20260730083000A1B2C3D4E5",

```

成功响应为 `204 No Content`，没有响应体。回调请求不使用用户 Token，必须由支付服务端调用。

当前实现的环境行为：`WECHAT_PAYMENT_MODE=mock` 时进入 mock 处理；`real` 时返回 `503`，响应示例为 `{"detail":"WeChat payment callback verification is not configured"}`。回调字段校验失败返回 `422`；订单不存在返回 `404`；订单已处于不可支付状态返回 `409`。由于当前订单 `product_type` 与套餐编码存在已知问题，mock 联调前应先修复该问题。

### 6.15 兑换积分商品或权益

```http
POST /api/v1/users/me/points/redeem
Authorization: Bearer <access_token>
Idempotency-Key: redeem-user-1001-extra-20260730-01
Content-Type: application/json

{
  "product_code": "extra_apply"
}
```

成功响应 `200`：

```json
{
  "order_no": "PT20260730082000ABCDEF1234",
  "product_code": "extra_apply",
  "product_name": "额外申请次数",
  "points_cost": 20,
  "status": 1,
  "balance": 125
}
```

`status=1` 表示该商品对应的额度已经自动发放；未映射的商品返回 `status=0`，表示待履约。相同用户重复使用相同 `Idempotency-Key` 会返回原兑换订单和当前余额，不会再次扣分。

兑换错误示例：

| 状态码 | 条件 | 示例 |
| ---: | --- | --- |
| `404` | 商品不存在或已下架 | `{"detail":"积分商品或权益不存在"}` |
| `409` | 库存不足 | `{"detail":"积分商品库存不足"}` |
| `409` | 积分余额不足 | `{"detail":"积分余额不足"}` |
| `422` | 缺少幂等键或长度超过 128 | `{"detail":"请提供有效的 Idempotency-Key"}` |
| `422` | 商品 `value` 不是有效数量 | `{"detail":"积分商品权益数量配置无效"}` |

## 7. 当前未完成和已知风险

以下内容不能作为当前已实现能力对外承诺：

1. 真实微信支付 API v3 请求、回调验签、金额校验、退款和对账。
2. 会员续费顺延、退款后的权益回收和过期状态自动更新。
3. 创建订单的 `product_type` 与回调套餐编码关联问题。
4. 邀请注册/实名事件自动推进及邀请积分入账。
5. 积分兑换订单履约、取消、退款、冲正、实物发货和后台操作接口。
6. `profile_detail_unlock` 等未映射商品的权益发放。
7. 积分冻结、积分过期、批次扣减和后台积分调整审计。
8. 真实 MySQL 并发、支付回调和兑换流程的集成验收。

## 8. 修改代码时必须保持的约束

- 所有会员、积分和额度权限以服务端数据库/Redis 状态为准，不能信任前端提交的 `is_vip`、余额、价格、有效期或剩余次数。
- 支付金额、套餐天数和商品权益必须从服务端配置读取。
- 签到、任务领取、会员订单和积分兑换必须保持幂等；兑换请求必须携带 `Idempotency-Key`。
- 积分流水、兑换订单、额外额度发放和库存扣减必须处于一致的事务边界内。
- 会员和积分接口的字段、状态、错误码变化必须同步更新 `docs/api/会员.md`、`docs/api/积分.md` 和本文件。
- 生产环境不能使用 mock 支付；敏感密钥只能通过环境变量或配置中心提供。
