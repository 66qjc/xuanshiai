## 1. 使用方式

- `P0`：阻塞安全、资金、隐私、主流程联调或一期验收，必须先完成。
- `P1`：阻塞模块完整验收，应在正式发布前完成。
- `P2`：AI、迁移、运营增强或可明确延期的能力。
- 每个工作项必须按“设计评审、数据迁移、后端实现、前端联调、自动化测试、产品验收”六个环节关闭。
- 未完成依赖项时，不得把后续工作项标记为完成。

## 2. 总体执行流程

1. 完成 G-01，冻结所有冲突口径和一期范围。
2. 完成 G-02 至 G-04，统一权限、数据范围、幂等、审计、状态机和接口契约。
3. 优先完成红娘和消息 P0 主流程，修复资金、隐私、通知和双认证问题。

6. 前端按业务场景联调，产品按验收标准确认。

# 第一部分：公共基础与产品决策

## G-01 冻结产品口径与一期验收边界

**优先级：P0，产品决策**

### 修改理由

产品导图、例会调整、旧平台补充文档之间存在联系方式展示、热心红娘点击行为、排行指标、私人定制阶段、社区 Tab、纸飞机认证、AI 隐私和现金/积分计费等冲突。不先形成唯一决议，接口状态机、字段和验收用例都会反复修改。

### 修改方案

建立产品决策表，XMind 与例会资料决定架构，四份 Markdown 只补充接口字段；每个冲突项必须给出唯一口径、一期范围、责任人和生效日期。

### 详细实施步骤

1. 建立 `docs/产品口径决策表-红娘社区消息.md`，逐项登记冲突编号、来源、候选方案、最终决议和影响接口。
2. 由产品确认红娘电话/微信是公开展示、付费后交付还是双方授权后交付。
3. 确认热心红娘卡片是否可点击，以及排行榜唯一指标是介绍人数、完成服务数、评分还是组合分。
4. 确认私人定制一期是否上线；若上线，冻结三档套餐与七阶段履约；若不上线，从一期菜单和验收清单移除。
5. 确认社区主 Tab 使用“关注”还是“喜欢”，并冻结各 Tab 对应的 feed mode。
6. 确认纸飞机匿名建档、扔/捡、回复、资料解锁各动作的实名认证和人脸认证门槛。
7. 确认申请拒绝、超时、撤回的返次规则，以及 AI 匹配、爆灯使用现金还是积分。
8. 确认 AI 分身聊天记录的可见主体、保存周期、删除权和取证例外。

### 业务流程

- 产品提出决议 -> 技术评审状态机和数据影响 -> 前端确认页面行为 -> 测试编写验收矩阵 -> 负责人签字冻结。

### 接口与数据改动

本项原则上不新增接口；决议后更新 OpenAPI 描述、状态枚举和错误码。

### 验收标准

- 所有评估报告中的模糊点和 X1-X16 矛盾项都有唯一结论。
- 任何一期页面都能指向确定的接口、状态机和权限前置条件。
- 后续需求变更必须新增决策记录，不允许直接覆盖历史口径。

### 测试要求

- 由测试把决策表转换为端到端验收用例。

### 依赖关系

无，其他 P0 项均依赖本项。

## G-02 落地红娘后台 RBAC、组织数据范围与统一认证

**优先级：P0，安全阻断项**

### 修改理由

最新代码已保存红娘后台账号权限，但 `/admin/matchmaker/auth/me` 仍返回固定权限，所有红娘后台路由只校验登录；账号、会员、门店、财务和约见接口没有组织范围过滤。安排约见还使用普通管理员 Token，而查询和修改使用独立红娘后台 Token，存在越权和单流程双登录问题。

### 修改方案

保留独立红娘后台认证，但建立真实权限码、角色、组织范围解析和统一依赖；同一红娘商家后台流程全部使用独立 Token，平台超级管理员通过明确的跨域授权访问。

### 详细实施步骤

1. 定义角色：平台超级管理员、平台运营、机构管理员、门店管理员、红娘、财务、只读审计员。
2. 定义权限码并按资源和动作拆分，例如 `matchmaker.account.write`、`member.read`、`finance.refund`、`meeting.schedule`。
3. 给账号增加 `data_scope`，至少支持 `SELF`、`STORE`、`ORGANIZATION`、`ALL`，并保存可访问组织集合。
4. 在依赖层实现 `require_matchmaker_permission(permission)` 和数据范围上下文。
5. 逐个改造账号、会员、门店、资源分配、财务、约见、服务单、活动和 CRM 路由，禁止仅依赖“已登录”。
6. 将约见安排接口从普通管理员依赖迁移到独立红娘后台权限；若保留平台管理员入口，使用单独路径和审计主体。
7. 修改 `/admin/matchmaker/auth/me`，返回数据库真实权限、角色、数据范围和绑定红娘/组织。
8. 所有 SQL 查询统一追加数据范围条件，写入前再次校验目标资源属于可访问范围。
9. 增加权限变更后会话刷新或强制失效策略，避免旧 Token 长期保留权限。

### 业务流程

- 登录 -> 加载账号角色和范围 -> 路由校验权限码 -> 服务层校验目标资源范围 -> 执行业务 -> 写审计。

### 接口与数据改动

修改红娘后台登录态响应；统一约见安排鉴权；必要时增加角色、权限和账号组织绑定管理接口。

### 验收标准

- 任意有效账号不再天然拥有全部后台能力。
- 门店账号不能读取或修改其他门店会员、订单、约见和财务数据。
- 同一个红娘后台 Token 可以完成约见查询、安排和更新。
- 权限不足统一返回 403，资源不在范围内按安全策略返回 403 或 404。

### 测试要求

- 覆盖每种角色的允许/拒绝矩阵。
- 覆盖跨门店、跨组织、绑定红娘 SELF 范围和权限变更后的旧会话。

### 依赖关系

依赖 G-01；阻塞全部后台写接口验收。

## G-03 统一幂等、审计、通知事件和事务边界

**优先级：P0**

### 修改理由

最新后台账号文档要求写操作提供 `Idempotency-Key`，但新增账号、会员、门店成员等路由未接入幂等依赖；服务分配、约见、退款、通知又跨多张表。不统一会产生重复账号、重复履约、重复通知或业务成功但审计失败。

### 修改方案

建立统一命令执行模板：鉴权和范围校验 -> 幂等占位 -> 状态机校验 -> 业务写入 -> 审计/事件 Outbox 同事务提交 -> 异步投递。

### 详细实施步骤

1. 列出所有必须幂等的 POST/PATCH，包括账号创建、会员创建、门店成员添加、资源改派、约见安排、退款、申请处理和消息发送。
2. 复用或扩展现有幂等服务，唯一键至少包含调用主体、接口、业务键和 `Idempotency-Key`。
3. 相同键相同请求返回首次结果；相同键不同请求返回 409；处理中重试返回明确状态。
4. 扩展审计日志字段：主体类型、主体 ID、权限码、组织、修改前后快照、原因、请求 ID、IP。
5. 建立统一业务事件/Outbox 表，事件包含类型、业务 ID、接收人、去重键、导航目标和重试次数。
6. 服务单、约见、申请、活动、公告和聊天通过统一事件服务生成站内通知。
7. 确保业务写入、审计和 Outbox 在同一数据库事务；外部微信/推送在提交后异步处理。
8. 实现失败重试、死信和人工重放工具，并保证消费者幂等。

### 业务流程

- 请求到达 -> 校验幂等键 -> 执行业务事务 -> 记录审计与 Outbox -> 返回结果 -> Worker 投递通知。

### 接口与数据改动

所有关键写接口声明 `Idempotency-Key`；增加事件重试/死信后台接口，仅限运维权限。

### 验收标准

- 重复提交不产生重复账号、订单、分配、约见或消息。
- 每个敏感写操作都有可检索审计记录。
- 通知失败不回滚已成功业务，重试也不重复发送。

### 测试要求

- 并发相同键、相同键不同 Body、事务回滚、Outbox 重试和死信重放测试。

### 依赖关系

依赖 G-02 的主体和权限模型。

## G-04 统一状态机、时间口径、错误码与接口文档

**优先级：P0**

### 修改理由

当前补充 Markdown 存在旧路径，新增两份后台文档又主要是接口清单，未达到项目规则要求；申请返次使用 UTC 同日判断，产品却没有明确时区和边界。状态、时间和错误码不统一会直接导致前端联调分支错误。

### 修改方案

为红娘、社区和消息建立状态机与接口契约字典，统一使用数据库 UTC 存储、业务时区 Asia/Shanghai 计算自然日，并按项目模板补全 `docs/api/*`。

### 详细实施步骤

1. 为申请、服务单、订单、约见、活动、纸飞机会话、聊天消息和通知分别画状态转换表。
2. 标明每个状态允许的操作者、前置状态、后置状态、副作用、退款/返次和通知。
3. 冻结业务自然日时区，所有“当天”“过期”“撤回窗口”使用可配置时区计算。
4. 建立业务错误码前缀和 HTTP 映射，禁止同一错误在不同接口返回 400、409、422 三种结果。
5. 为 264 个当前 OpenAPI 路径建立文档覆盖检查，旧路径只进入迁移映射，不作为联调契约。
6. 按项目模板补请求字段表、非法示例、响应字段展开、空数据示例、调用顺序、幂等和错误码。
7. 在 CI 中生成 OpenAPI 并检查 operationId、路径、方法、响应模型与文档索引。

### 业务流程

- 状态机评审 -> Schema 和服务修改 -> OpenAPI 更新 -> 文档更新 -> 契约测试 -> 前端联调。

### 接口与数据改动

不限定新增接口，主要规范现有接口契约。

### 验收标准

- 任何状态变化都有唯一合法路径和错误码。
- 同一自然日规则在测试、服务和文档中一致。
- 新增后台接口文档达到 PROJECT_RULES.md 的完整度要求。

### 测试要求

- 状态转换参数化测试、时区边界测试、OpenAPI 快照和文档覆盖测试。

# 第二部分：红娘模块

## M-01 建设红娘申请审核工作台与公开资料发布流程

**优先级：P0**

### 修改理由

当前只能按已知申请 ID 审核，没有正常的申请列表和详情工作台；申请资料虽含微信、头像、擅长领域、价格和案例，但审核通过后没有发布为公开红娘资料的明确流程。

### 修改方案

拆分“申请材料”和“公开红娘档案”，建立申请列表、详情、审核、发布、退回补充、停用和版本审计闭环。

### 详细实施步骤

1. 增加申请分页接口，支持类型、状态、组织、提交时间、审核时间、手机号/昵称搜索。
2. 详情接口返回完整申请字段、材料、历史审核记录和可执行动作。
3. 审核动作支持通过、拒绝、退回补充；要求原因并使用乐观锁防止重复审核。
4. 审核通过时事务内创建或更新公开红娘档案，但敏感联系方式只写受控字段。
5. 公开档案支持草稿、待发布、已发布、已停用状态，并保留发布版本。
6. 增加后台资料编辑、上下线和停用接口；停用时处理在途订单、服务单和预约。
7. 向申请人发送审核结果和补充材料通知。

### 业务流程

- 提交申请 -> 工作台筛选 -> 查看详情 -> 审核/退回 -> 生成公开档案草稿 -> 运营确认发布 -> C 端可见。

### 接口与数据改动

新增申请列表/详情/审核历史；新增公开档案后台详情、编辑、发布、停用接口。

### 验收标准

- 后台无需预先知道申请 ID 即可完成审核。
- 审核通过不会自动公开敏感字段。
- 每次审核和发布均可追溯，重复审核返回 409。

### 测试要求

- 列表筛选、并发审核、退回再提交、停用在途业务和敏感字段脱敏测试。

### 依赖关系

依赖 G-02、G-03。

## M-02 补齐红娘公开主页、成功案例和评价治理

**优先级：P1**

### 修改理由

公开卡片缺少擅长领域、价格摘要、成功案例、故事图片、个性签名和服务内容；申请材料不能替代公开内容。没有评价治理也无法可靠生成评分。

### 修改方案

建立公开档案、案例和评价三类模型，后台审核后发布，C 端只读取已发布且允许公开的数据。

### 详细实施步骤

1. 扩展公开档案字段：签名、介绍、擅长领域、服务内容、服务方式、价格摘要、认证标签。
2. 建立成功案例表，区分草稿、待审、已发布、驳回、下线，图片引用受控媒体资源。
3. 建立服务评价表，仅完成且未全额退款的真实服务参与人可评价，每个服务和用户最多一次。
4. 评价支持评分、标签、文字、匿名展示和举报；后台支持隐藏、恢复和审计。
5. 聚合评分、评价数、成功服务数和案例数，避免每次列表实时扫表。
6. 更新 C 端红娘卡片和详情响应，明确空值和隐藏规则。

### 验收标准

## M-03 统一红娘联系方式展示与授权交换

**优先级：P0，产品决策后实施**

### 修改理由

产品资料存在电话/微信直接显示与付费/授权后交付两种口径。当前代码既有红娘微信交付又有双方联系方式交换，如果前端直接读取公开字段会造成隐私泄露和付费绕过。

### 修改方案

采用分级可见模型：公开页只返回展示状态和脱敏信息；完整联系方式通过有效订单、服务单状态或双方授权生成一次性授权记录后读取。

### 详细实施步骤

1. 根据 G-01 决议定义联系方式可见条件和优先级。
2. 公开 Schema 删除完整手机号/微信，增加 `contact_visibility`、脱敏值和可申请动作。
3. 创建授权记录，保存授权双方、来源服务单、范围、过期时间、撤销状态和审计。
4. 读取完整联系方式时校验当前用户、服务状态、授权范围和有效期。
5. 支持用户撤销尚未被读取的授权；已读取后保留审计但不重复暴露。
6. 服务退款、取消、红娘停用时按决议撤销后续访问。
7. 对日志、错误信息和通知载荷执行脱敏。

### 业务流程

- 查看红娘主页 -> 发起咨询/购买 -> 红娘接受或双方授权 -> 生成授权 -> 指定主体读取一次或限时读取 -> 审计。

### 接口与数据改动

保留现有 contact exchange 能力并统一返回模型；禁止公开详情直接返回完整联系方式。

### 验收标准

- 未满足条件的用户无法通过任何接口获得完整联系方式。
- 授权、读取、撤销和过期均有审计。
- 前端能区分“不可见、可申请、待授权、已授权、已过期”。

### 测试要求

- IDOR、跨服务单读取、过期、撤销、退款和日志脱敏测试。

### 依赖关系

依赖 G-01、G-02、G-03。

## M-04 实现 1v1 咨询预约、时段库存和支付确认闭环

**优先级：P1**

### 修改理由

### 修改方案

2. 红娘后台配置周期规则、例外日期、休息时间和最大并发。

6. 支持双方可配置范围内改期和取消，并联动退款、通知及日历。

### 业务流程

### 接口与数据改动

### 验收标准

- 并发选择同一时段最多一人成功。

- 所有改期取消都正确联动退款和通知。

### 测试要求

- 并发锁、支付回调重复、锁超时、跨时区、改期冲突和退款测试。

### 修改方案

6. 定时任务扫描待响应和待服务超时单，按产品规则自动取消、升级或退款。

### 验收标准

### 测试要求

## M-09 统一财务和约见后台身份、数据范围与敏感操作

**优先级：P0**

### 修改理由

财务接口现已改用独立红娘后台账号，但没有细粒度财务权限和组织过滤；约见安排仍使用普通管理员身份。退款、分成释放、提现审核和私密约见反馈属于高风险操作。

### 修改方案

所有商家后台财务与约见操作统一使用独立后台主体，按组织/门店限制数据，并对退款、提现、分成和私密反馈设置专门权限、二次确认和审计。

### 详细实施步骤

1. 统一财务和约见路由鉴权依赖，平台管理员通过显式平台入口访问。
2. 订单、总账、提现和报表查询按订单归属组织过滤。
3. 退款、分成释放、提现审核分别使用独立权限码，要求原因和幂等键。
4. 高金额退款或提现增加双人复核或审批状态。
5. 约见安排、改期、取消和反馈查询按服务单归属过滤。
6. 私密反馈默认仅指定运营/风控权限可见，红娘本人只看允许公开的摘要。
7. 后台账号 ID 与普通用户 ID 在审计中使用主体类型区分，禁止混淆。
8. 补充导出接口时执行脱敏、水印、最大行数和导出审计。

### 业务流程

- 后台查询范围内业务 -> 发起敏感操作 -> 权限与额度校验 -> 必要时复核 -> 执行 -> 审计和通知。

### 接口与数据改动

修改现有 `/admin/finance/*`、`/admin/matchmaker/meetings/*` 权限；可增加审批和导出任务接口。

### 验收标准

- 单一红娘后台登录可完成授权范围内的约见流程。
- 非财务账号无法退款、释放分成或审核提现。
- 私密反馈不会被无关红娘或门店账号读取。

### 测试要求

- 跨组织财务读取、高金额双审、重复退款、约见跨店访问和私密反馈权限测试。

### 依赖关系

依赖 G-02、G-03。

## C-03 完成活动支付、审核、取消、签到和奖励闭环

### 修改方案

### 测试要求

## C-04 完成纸飞机匿名身份、收回、资料解锁和媒体权限

**优先级：P1**

### 修改理由

现有纸飞机消息基础能力不能覆盖匿名头像昵称、扔/捡/我的、收回、举报、积分解锁资料、语音媒体权限和结束对话。

### 修改方案

建立独立匿名身份、飞机状态、会话权限和解锁订单，匿名标识不得直接暴露真实用户 ID。

### 详细实施步骤

1. 首次进入生成或选择匿名头像昵称，保存版本和可重置规则。
2. 定义飞机状态：可捡、已捡、会话中、已收回、已结束、已删除。
3. 扔和捡使用配额及并发锁，保证一架飞机只被一个有效用户捡取。
4. 发送文字/语音前校验会话参与者、认证门槛、封禁和媒体归属。
5. 发送者可在未被捡或产品允许窗口内收回；收回后不可建立新会话。
6. 资料解锁创建积分扣减记录和授权记录，失败时返还积分。
7. 解锁只返回产品允许的资料字段，不直接开放完整档案或联系方式。
8. 支持结束对话、举报、拉黑和双方视角的“我的飞机”列表。

### 业务流程

- 匿名建档 -> 扔飞机 -> 他人捡取 -> 建立匿名会话 -> 互动 -> 可选积分解锁 -> 结束/举报/收回。

### 接口与数据改动

新增匿名身份、扔/捡/收回、我的飞机、资料解锁、结束会话接口；完善媒体消息。

### 验收标准

- 匿名接口不泄露真实用户 ID。
- 同一飞机不会被并发重复捡取。
- 积分扣减、授权和退款可审计。

### 测试要求

- 并发捡取、收回竞争、媒体越权、解锁失败返还、举报封禁和匿名泄露测试。

### 依赖关系

依赖 C-01、积分、G-03。

## MSG-01 统一申请认识的返次、撤回、过期和状态机

**优先级：P0**

### 修改理由

产品要求拒绝返还一次机会，代码只在同一 UTC 日期拒绝时返还；撤回和过期规则也不完整，容易产生额度争议。

### 修改方案

按产品决议建立额度流水和完整申请状态机，不直接靠“当前日期是否相同”修改计数。

### 详细实施步骤

1. 冻结发送、接受、拒绝、撤回、过期、取消和封禁终止状态。
2. 定义每种终态是否返次、返多少、使用业务时区还是固定时长。
3. 建立申请额度流水，扣减和返还使用唯一业务键。
4. 发送申请时事务内扣减额度并创建申请。
5. 接受/拒绝/撤回使用条件更新防止双方并发处理。
6. 定时任务处理过期并执行返次和通知。
7. 提供用户可查看的额度变动原因。

### 业务流程

- 发送申请并扣次 -> 对方接受/拒绝；发送方可在窗口内撤回；超时任务过期 -> 按规则返次 -> 通知双方。

### 验收标准

- 任何申请最多返还一次。
- 上海时区/固定时长规则与产品文档一致。
- 并发接受和拒绝只能一个成功。

### 测试要求

## MSG-02 同意申请后事务内创建会话和自动欢迎消息

**优先级：P0**

### 修改理由

当前同意申请会创建匹配和会话，但没有产品要求的自动开场消息，用户进入空会话。若分步执行还可能出现已匹配但无会话或重复欢迎消息。

### 修改方案

2. 为申请 ID 与会话建立唯一约束。
3. 接受命令锁定申请并检查当前状态。
4. 创建或复用匹配关系和会话。
5. 以申请 ID 作为唯一键插入欢迎消息。
6. 写双方通知事件并提交事务。
7. 重复接受返回首次结果，不新增消息。

### 业务流程

- 接收方点击同意 -> 状态校验 -> 创建匹配/会话/欢迎消息 -> 通知 -> 双方进入同一会话。

### 接口与数据改动

### 验收标准

- 事务任一步失败都不留下半成品。

### 测试要求

- 重复接受、双方并发、事务注入失败和未读计数测试。

### 依赖关系

依赖 MSG-01、G-03。

## MSG-03 补会话置顶、删除/隐藏、分页和送达状态

**优先级：P1**

### 修改理由

产品要求置顶和删除，当前只有隐藏字段且无接口；聊天记录数组缺少稳定分页契约，也没有完整送达状态。

6. 已读接口推进最大已读消息 ID，不逐条写无界记录。

### 业务流程

### 接口与数据改动

### 验收标准

### 依赖关系

依赖 G-03、C-05。

## MSG-06 建设实时聊天传输、在线状态和可靠投递

**优先级：P1 或 P2**

### 修改理由

现有 HTTP 收发可用于基础联调，但产品级聊天需要实时到达、断线重连、多端同步、顺序和重复处理。

### 修改方案

数据库消息为真源，WebSocket/推送只传事件；使用会话序号和游标完成补偿。

### 详细实施步骤

1. 定义连接鉴权、心跳、断线、踢下线和多端策略。
2. 消息持久化成功后通过 Outbox 发布实时事件。
3. 事件包含 message_id、conversation_id、sequence 和 client_message_id。
4. 客户端重连携带最后序号，服务端补发缺失事件。
5. 跨实例使用 Redis Streams 或可靠消息系统，不只使用进程内广播。
6. 实现限流、背压、慢消费者和最大连接数保护。
7. 在线状态设置过期时间，不能作为隐私敏感精确轨迹公开。

### 业务流程

- HTTP/WS 发送 -> 持久化 -> Outbox -> 实时投递 -> 客户端确认；断线后按游标补拉。

### 接口与数据改动

新增 WebSocket 入口、事件协议和同步接口；保留 HTTP 作为可靠回退。

### 验收标准

- 断线重连不丢消息、不重复展示。
- 多实例部署仍能正确投递。
- 实时层故障不丢数据库消息。

### 测试要求

- 乱序、重复、断线、多端、跨实例、慢消费者和高并发测试。

### 依赖关系

依赖 MSG-03、G-03。

## MSG-07 建设消息管理后台和证据保全流程

**优先级：P1**

### 修改理由

消息后台基本缺失，举报审核时缺少受控取证；直接开放聊天全文又会严重侵犯隐私。

### 修改方案

后台默认只看举报上下文和脱敏元数据，扩大查看范围必须具备权限、理由、审计和时限。

### 详细实施步骤

1. 建立消息举报与证据快照，保存举报时必要上下文和内容哈希。
2. 后台列表按举报状态、风险类型、时间和会话筛选。
3. 普通审核员只看最小上下文；查看更大范围需高级权限和原因。
4. 撤回/删除消息的证据保留期限按合规决议执行。
5. 所有查看、导出、封禁和证据下载写不可抵赖审计。
6. 导出文件加水印、过期和访问次数限制。
7. 处理结果通知举报人和被处理人，避免暴露对方隐私。

### 业务流程

- 用户举报 -> 固化证据 -> 审核员最小查看 -> 处理/升级 -> 审计 -> 通知 -> 到期清理。

### 接口与数据改动

新增消息举报、后台队列、证据查看、处理和受控导出接口。

### 验收标准

- 无举报或授权理由不能任意搜索聊天全文。
- 撤回消息仍可按合规规则取证。
- 每次敏感访问可追溯。

### 测试要求

- 越权查看、扩大范围审批、撤回证据、导出过期和审计完整性测试。

### 依赖关系

依赖 G-02、G-03。

## MSG-08 冻结并实现 AI 分身、AI 军师的隐私边界

**优先级：P2**

### 修改理由

资料对“用户可看 AI 分身聊天记录”和“分身主人不能知道别人聊了什么”存在直接矛盾。未冻结数据控制者和可见主体前不能上线。

### 修改方案

先完成隐私决议，再将 AI 分身会话与真人会话隔离；默认分身主人只能看汇总反馈，不看第三方原始聊天。

### 详细实施步骤

1. 明确分身主人、对话用户、平台的访问权和删除权。
2. 定义是否允许训练、数据保留期、敏感信息处理和取证例外。
3. AI 分身会话使用独立 conversation type 和权限策略。
4. 向对话用户明确提示正在与 AI 交互。
5. 分身主人只接收经脱敏的兴趣/匹配摘要，除非产品和合规明确允许原文。
6. AI 军师读取真人聊天必须获得用户主动授权并限制时间范围。
7. 增加模型安全审核、成本配额、人工投诉和一键停用。

### 业务流程

- 用户授权/进入 AI -> 权限和隐私提示 -> 对话 -> 安全审核 -> 保存受控记录 -> 生成允许范围内摘要 -> 删除/投诉。

### 接口与数据改动

新增 AI 分身资料、会话、授权、摘要、删除和投诉接口。

### 验收标准

- 任何角色的可见字段与 G-01 决议一致。
- 真人聊天不会被 AI 军师默认全量读取。
- 用户可撤销授权并触发后续访问失效。

### 测试要求

- 角色可见性、授权撤销、提示注入、敏感信息和删除传播测试。

### 依赖关系

依赖 G-01；未决议前禁止上线。

# 第五部分：测试、迁移与发布

## T-01 补真实 MySQL、Redis 和 HTTP 端到端测试

**优先级：P0**

### 修改理由

当前测试为 199 通过、13 跳过；9 个实时 HTTP 用例未设置 LIVE_API_BASE，4 个社区数据库用例未配置测试库。最新账号、会员、门店、财务和约见后台没有专项测试，现有通过结果不能证明真实 SQL、事务和权限可靠。

### 修改方案

建立独立测试基础设施，将关键状态机、权限隔离、并发和外部回调纳入 CI 必跑。

### 详细实施步骤

1. 配置独立 MySQL 测试库和 Redis，禁止连接开发或生产库。
2. CI 设置 `ENVIRONMENT=testing`、`COMMUNITY_TEST_DATABASE_URL` 和测试服务地址。
3. 把 13 个跳过用例拆分为 CI 必跑集和明确的外部沙箱集。
4. 红娘覆盖账号、会员、门店、资源、财务、约见、支付激活和服务改派。
5. 社区覆盖活动、纸飞机、话题/Banner、审核、分享和统计。
6. 消息覆盖申请额度、自动欢迎、会话操作、通知、公告、实时同步和举报取证。
7. 使用并发测试验证唯一约束、行锁、版本号和幂等。
8. 测试数据通过事务或命名空间清理，不依赖预置脏数据。

### 业务流程

- 创建隔离环境 -> 执行迁移 -> 准备最小数据 -> 跑契约/业务/并发/安全测试 -> 生成报告 -> 清理。

### 接口与数据改动

不新增业务接口；可增加测试专用健康检查，生产环境禁用。

### 验收标准

- 目标模块 CI 数据库测试无无条件跳过。
- P0 状态机、权限和幂等均有正反用例。
- 测试可重复运行且不污染其他环境。

### 测试要求

- 本项即测试总计划，并要求保留覆盖率和失败日志。

### 依赖关系

依赖各业务项接口稳定。

## T-02 实施数据库迁移、历史回填和回滚演练

**优先级：P0**

### 修改理由

清单涉及权限范围、阶段履约、匿名身份、额度流水、公告、事件 Outbox 等结构。生产禁止启动时自动改表，没有迁移和回滚会导致上线失败或历史数据语义错误。

### 修改方案

所有结构和数据变化使用版本化迁移，先兼容写入再切换读取，最后清理旧结构。

### 详细实施步骤

1. 为每个工作项列出表、列、索引、唯一约束和数据量影响。
2. 迁移脚本检查前置版本并可重复安全执行。
3. 大表索引和字段变更评估锁表，必要时采用在线变更。
4. 为旧通知、服务分配、会话隐藏和红娘权限编写回填规则。
5. 回填后核对数量、外键语义、状态分布和孤儿数据。
6. 发布采用 expand -> backfill -> dual read/write -> switch -> contract。
7. 在生产结构副本演练前滚和回滚，记录耗时与恢复点。
8. 生产保持 `AUTO_INIT_DB=false`。

### 业务流程

- 结构扩展 -> 部署兼容代码 -> 回填校验 -> 切换读写 -> 观察 -> 清理旧结构。

### 接口与数据改动

迁移期间接口保持兼容；破坏性字段变更必须给废弃周期。

### 验收标准

- 迁移可在生产副本成功演练。
- 回滚不会丢失合法新业务数据。
- 历史记录在新状态机下有明确映射。

### 测试要求

- 迁移前后数量校验、重复执行、失败恢复和性能测试。

### 依赖关系

依赖各项数据设计冻结。

## T-03 完成接口文档、联调样例和验收追踪

**优先级：P0**

### 修改理由

四份 Markdown 仅是旧平台补充，不能修改架构；当前新增后台文档仍偏清单化。若文档、OpenAPI、前端和代码不一致，完成度无法客观验收。

### 修改方案

以当前 `/api/v1/*` OpenAPI 为接口真源，以产品决策表为业务真源，为每项建立需求到接口到测试的追踪矩阵。

### 详细实施步骤

1. 每个新增或修改接口同步更新 `docs/api/*`。
2. 按 PROJECT_RULES.md 补全 URL、方法、鉴权、权限、请求字段、非法示例、响应字段、空数据、状态机、错误码和调用顺序。
3. 建立旧 `/loveadmin/*`、`/commonadmin/*` 到新路径的迁移映射，禁止前端继续猜测。
4. 生成前端联调示例，覆盖成功、空数据、权限不足、状态冲突和幂等重试。
5. 建立追踪表：产品需求 -> 工作项 -> API -> 数据表 -> 测试 -> 验收记录。
6. OpenAPI 快照进入 CI，未更新文档的路径变更阻止合并。
7. 产品、前端、后端和测试按工作项验收标准签字。

### 业务流程

- 开发设计 -> 契约评审 -> 代码与文档同步 -> 自动检查 -> 前端场景联调 -> 产品验收。

### 接口与数据改动

文档治理，不新增业务接口。

### 验收标准

- 前端不查看源码即可完成联调。
- 四份补充 Markdown 被明确标记为参考，不覆盖架构决议。
- 所有 P0/P1 项都有接口和测试追踪。

### 测试要求

- OpenAPI 快照、文档路径覆盖、示例 Schema 校验。

### 依赖关系

依赖 G-04 和业务接口冻结。

## T-04 灰度发布、监控、告警和回退

**优先级：P1**

### 修改理由

权限、退款、未读、实时消息和匿名功能跨模块影响大，测试通过仍不能完全代表存量数据与真实并发。

### 修改方案

按组织和账号灰度，使用功能开关、关键指标和审计抽样控制风险；回退代码时不破坏已产生的合法数据。

### 详细实施步骤

1. 为 RBAC、活动支付、纸飞机、自动欢迎、公告和实时消息建立独立功能开关。
2. 先对内部账号和测试门店开放，再按组织逐步扩大。
3. 监控 401/403、跨范围拒绝、重复通知、幂等冲突、退款失败、未读漂移、消息延迟和 Outbox 堆积。
4. 对敏感后台查询和导出做每日审计抽样。
5. 设置业务告警阈值、值班责任人和处置手册。
6. 准备关闭新入口、切回 HTTP、暂停自动任务和人工补偿方案。
7. 灰度稳定后才废弃旧路径和兼容字段。
8. 发布后复盘缺陷并更新决策表和测试集。

### 业务流程

- 部署关闭功能 -> 内部灰度 -> 指标观察 -> 小组织灰度 -> 扩量 -> 全量 -> 清理兼容。

### 接口与数据改动

增加受控配置和内部监控，不向普通用户暴露运维接口。

### 验收标准

- 出现严重权限或资金异常可在分钟级关闭相关能力。
- 回退不删除新数据，不重复扣款或返次。
- 全量前完成至少一个完整灰度周期。

### 测试要求

- 开关切换、任务暂停恢复、告警演练和补偿脚本演练。

### 依赖关系

依赖 T-01、T-02、T-03。
