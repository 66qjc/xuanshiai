# 红娘、社区、消息模块详细修改方案

日期：2026-08-03  
适用范围：普通用户端、父母端、服务红娘端、超级管理员后台  
依据：三个 XMind、`PROJECT_RULES.md`、`docs/api/`、`no upload/` 和当前 `app/` 实现

## 1. 结论与已冻结口径

本方案吸收本次评估意见和产品补充说明。以下内容视为当前一期基线，不再按“待确认需求”处理：

| 事项 | 一期口径 |
| --- | --- |
| 免费红娘服务次数 | 不提供免费服务次数。热心红娘可以展示和排行，但不产生免费红娘服务订单。红娘服务通过付费订单开通。 |
| 会员不限次数牵线 | 一期不提供。后续如产品变更，可以在会员权益、额度和订单模块中增加，但必须重新更新接口契约和迁移方案。 |
| 双重认证 | 双重认证 = 实名认证（姓名 + 身份证） + 人脸识别认证。两项都通过后才算“双重认证”。不能用未定义的布尔字段替代。 |
| 举报处理 | 举报提交后进入人工审核。举报不会自动等同于封禁或删除，人工审核结论与实际处置分开记录。 |
| 总封禁数据 | 数据保留，不物理删除。普通用户端和父母端不展示被封禁用户的主页、帖子、评论、头像、相册、红娘案例等内容；聊天和证据按取证规则保留，但用户侧隐藏身份和内容。 |
| 聊天撤回 | 同时提供现有 `DELETE` 接口和语义明确的 `POST .../recall` 接口。两者执行同一撤回服务，由前端根据客户端版本和产品入口选择调用。 |
| 父母端 | 父母端是独立客户端，但复用同一个后端和同一套领域数据。后端提供受权限和服务状态控制的查询接口，父母端是否在页面展示微信/电话由前端产品决定；前端隐藏不能替代后端权限校验。 |

## 2. 总体改造原则

1. 普通认识申请、红娘服务申请、成为红娘申请使用不同资源、状态和接口，禁止复用同一张业务申请表的含义。
2. 社区、消息、红娘都复用统一的用户状态、实名状态、拉黑、封禁、限制和审计能力。
3. 所有敏感数据以“后端允许返回”为准，前端只负责交互和展示，不负责安全判断。
4. 举报、审核、处置、封禁、申诉和通知分成独立记录，支持追溯和审计。
5. 新接口必须同步更新 `docs/api/`，提供完整参数、响应、错误码、状态、幂等和兼容性说明。

## 3. 第 5 项：举报人工审核需求

### 3.1 适用举报对象

一期统一支持：

- 用户
- 帖子
- 评论和回复
- 聊天消息
- 纸飞机及纸飞机会话消息
- 红娘资料、红娘案例和红娘服务行为
- 活动及活动内容

用户举报继续使用社交安全接口；社区内容使用社区举报接口；消息和红娘举报应补齐对应的目标类型和后台查询能力。所有举报最终进入统一管理员审核体系。

### 3.2 举报提交流程

```text
用户选择举报对象
-> 获取举报原因字典
-> 提交目标类型、目标 ID、原因、说明和证据
-> 校验目标当前是否存在、是否可见、是否重复举报
-> 创建举报单
-> 保存证据和内容快照
-> 进入待审核队列
-> 向举报人返回受理结果
```

提交阶段只负责受理，不直接删除内容、不直接封禁用户。

### 3.3 举报单数据要求

建议复用现有举报模型并补充以下字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 举报单 ID |
| `target_type` | `user`、`post`、`comment`、`message`、`paper_plane`、`matchmaker`、`activity` |
| `target_id` | 被举报资源 ID |
| `reporter_user_id` | 举报人，仅管理员和举报人本人可见 |
| `reason_id` | 举报原因字典 ID |
| `description` | 举报人补充说明，用户侧按隐私规则返回 |
| `evidence_ids` | 图片、视频、聊天截图等证据 ID |
| `snapshot_id` | 举报时保存的目标内容快照 |
| `status` | `PENDING`、`IN_REVIEW`、`RESOLVED`、`REJECTED`、`CANCELLED` |
| `result` | 人工审核结论 |
| `action` | 实际处置动作，可为空或为多个动作 |
| `reviewed_by` | 审核管理员，仅管理员可见 |
| `reviewed_at` | 审核时间 |
| `audit_id` | 对应审核审计记录 |

用户接口不得返回举报人的身份、审核人的身份或被举报人可据此反推出举报人的信息。

### 3.4 人工审核状态流转

```text
PENDING -> IN_REVIEW -> RESOLVED
                       -> REJECTED
                       -> CANCELLED
```

规则：

- 同一用户对同一目标存在未终结举报时，重复提交返回 `409`。
- `RESOLVED` 和 `REJECTED` 为终态，不能直接改判。
- 需要改判时创建复审记录，不覆盖原审核结论。
- 审核结论和处置动作必须在同一事务中写入，或通过可靠的处置任务保证最终一致。
- 审核员查看聊天原文、证据原文和敏感资料时必须写审计日志。

### 3.5 结论与处置动作映射

| 审核结论 | 可执行动作 | 适用对象 |
| --- | --- | --- |
| `NO_VIOLATION` 举报不成立 | 保持原状，通知举报人结果 | 全部 |
| `CONTENT_VIOLATION` 内容违规 | 屏蔽内容、删除展示、敏感词替换、转人工复核 | 帖子、评论、消息、纸飞机 |
| `USER_RESTRICTION` 用户行为违规 | 限制发帖、评论、私信或申请认识 | 用户 |
| `ACCOUNT_BANNED` 严重违规 | 总封禁，隐藏用户侧全部公开资料 | 用户 |
| `MATCHMAKER_SUSPENDED` 红娘违规 | 下架服务、暂停接单、取消红娘资格 | 红娘 |
| `EVIDENCE_INSUFFICIENT` 证据不足 | 保留举报和证据，不改变内容状态 | 全部 |

一个举报单可以关联多个处置动作，但每个动作必须有独立的目标、执行结果和审计记录。举报单状态不能直接等同于用户封禁状态。

### 3.6 建议补充或统一的后台接口

以下接口应以现有管理员路由为基础补齐详细契约：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/v1/admin/reports` | 分页、筛选、排序查询举报单 |
| `GET` | `/api/v1/admin/reports/{report_id}` | 查询举报详情、快照、证据和关联对象 |
| `PATCH` | `/api/v1/admin/reports/{report_id}/review` | 提交人工审核结论和处置动作 |
| `GET` | `/api/v1/community/reports/mine` | 查询本人提交的举报及被举报处理结果 |
| `POST` | `/api/v1/community/reports/{report_id}/appeals` | 提交可申诉举报的复审申请 |
| `GET` | `/api/v1/admin/report-appeals` | 查询复审队列 |
| `PATCH` | `/api/v1/admin/report-appeals/{appeal_id}/review` | 处理复审 |

消息举报和红娘举报需要明确是否直接复用 `/admin/reports`，建议统一复用，以便后台只有一套审核队列和审计规则。

### 3.7 前端流程

```text
打开举报弹窗
-> 加载举报原因
-> 选择原因并填写说明
-> 可选上传证据
-> 提交举报
-> 显示“已提交人工审核”
-> 在举报记录页查看处理结果
-> 如允许申诉，进入申诉页提交补充理由和证据
```

前端不得展示“举报成功 = 对方已封禁”的提示。审核结果通知应携带 `target_type`、`target_id` 和 `report_id`，便于跳转到安全结果页面。

## 4. 第 7 项：总封禁后的数据保留与前端隐藏

### 4.1 需求定义

总封禁是账号操作限制，不是数据删除。系统需要同时满足：

- 数据库保留必要业务数据、举报数据、审核数据、聊天取证和审计日志。
- 普通用户端和父母端不能通过任何公开接口获取被封禁用户的公开资料和内容。
- 被封禁用户不能继续发帖、评论、点赞、关注、申请认识、发消息、发纸飞机或查看受保护资源。
- 管理员在具备权限且有业务理由时可以查看必要证据。
- 后台查看原文和导出证据必须产生审计记录。

### 4.2 数据可见性矩阵

| 数据类型 | 普通用户 | 父母端 | 被封禁本人 | 超级管理员 |
| --- | --- | --- | --- | --- |
| 用户主页 | 不展示，按不存在或不可用处理 | 不展示 | 不允许访问普通功能页 | 按权限查看 |
| 头像、相册 | 不展示 | 不展示 | 不展示给其他用户 | 可按审核权限查看 |
| 历史帖子 | 不展示 | 不展示 | 不展示 | 可查看违规证据 |
| 历史评论 | 不展示或保留必要墓碑 | 不展示或保留必要墓碑 | 不允许继续互动 | 可查看 |
| 红娘资料和案例 | 不展示 | 不展示 | 不可接单 | 可查看审核资料 |
| 历史聊天 | 双方用户侧隐藏或按脱敏规则保留必要占位 | 同普通用户 | 不允许继续发送 | 可在举报/治理场景查看 |
| 举报和审核记录 | 仅返回本人有权查看的结果 | 仅返回本人有权查看的结果 | 按申诉规则返回 | 完整可见 |
| 审计日志 | 不可见 | 不可见 | 不可见 | 仅审计权限可见 |

公开查询接口建议统一采用“资源不可见返回 `404`”策略，避免通过 `403` 或错误差异泄露用户是否存在。后台接口则根据管理员权限返回明确的资源状态。

### 4.3 封禁与内容状态分离

不能只修改 `user.status` 来实现总封禁。至少需要区分：

- 用户账号状态：正常、总封禁、注销、冻结
- 用户功能限制：限制发帖、评论、私信、申请认识
- 内容状态：正常、审核中、屏蔽、删除、违规证据保留
- 聊天消息状态：正常、撤回、用户侧隐藏、管理员屏蔽、证据保留
- 红娘资格状态：有效、暂停、取消资格

这样可以支持部分限制、解封恢复和历史证据保留，不会把一次封禁误写成物理删除。

### 4.4 总封禁流程

```text
管理员提交总封禁请求
-> 校验管理员权限和目标用户
-> 填写原因、生效时间、结束时间、处理备注
-> 锁定用户限制记录
-> 写入总封禁限制
-> 关闭或隐藏公开资料、帖子、评论、红娘案例
-> 禁止新业务操作
-> 隐藏普通用户侧聊天和关系入口
-> 保留聊天、举报、证据和审计数据
-> 写入管理员操作日志
-> 向受影响用户发送治理结果通知
```

重复提交同一生效中的总封禁应返回当前限制记录，不重复创建限制。解除封禁只解除对应限制，不删除原封禁记录。

### 4.5 建议补充后台接口

```http
GET /api/v1/admin/users/{user_id}/restrictions
PATCH /api/v1/admin/users/{user_id}/restrictions
DELETE /api/v1/admin/users/{user_id}/restrictions/{restriction_id}
GET /api/v1/admin/users/{user_id}/moderation-history
GET /api/v1/admin/chat/sessions/{session_id}/messages
```

`PATCH /restrictions` 的请求至少需要：

```json
{
  "restriction_type": "TOTAL_BAN",
  "reason_code": "SERIOUS_VIOLATION",
  "reason": "人工审核确认严重违规",
  "starts_at": "2026-08-03T10:00:00Z",
  "ends_at": null,
  "note": "保留证据，禁止对外展示"
}
```

其中 `restriction_type` 至少支持：

- `TOTAL_BAN`
- `POST_RESTRICTED`
- `COMMENT_RESTRICTED`
- `MESSAGE_RESTRICTED`
- `APPLICATION_RESTRICTED`

### 4.6 前端处理规则

- 公开接口收到 `404` 时展示“用户暂不可见”，不能显示“用户已被封禁”或泄露治理原因。
- 被封禁用户自己的客户端显示账号受限页面，不展示公开资料和互动按钮。
- 聊天列表过滤不可用会话；如保留会话占位，只显示“当前对话不可用”，不返回对方真实资料。
- 后台治理结果通知只显示给有权知道结果的用户。
- 前端不得用本地缓存继续展示已被封禁的头像、帖子和案例；收到治理通知后应清理缓存。

## 5. 第 10 项：父母端复用后端的接口与流程

### 5.1 系统边界

父母端是独立客户端和独立产品界面，但不新增一套后端业务。它复用：

- 同一用户体系
- 同一实名认证和账号状态
- 同一红娘、订单、服务申请和联系方式数据
- 同一举报、封禁、审计和通知体系
- 同一 `/api/v1` 接口前缀和认证方式

父母端使用父母账号自己的 Access Token。后端根据账号身份、服务订单归属、授权状态和账号限制决定返回什么数据。

### 5.2 父母端推荐调用顺序

```text
父母端登录/绑定手机号
-> 查询当前用户资料和认证状态
-> 查询可用红娘商品
-> 查询公开红娘列表或指定红娘详情
-> 创建红娘服务订单
-> 调用支付流程
-> 查询订单状态
-> 支付成功后开通红娘服务
-> 查询自己的服务申请
-> 查询红娘联系方式
```

父母端不应调用普通用户的“申请认识”接口来替代红娘服务订单，也不能通过普通用户资料接口读取红娘私密联系方式。

### 5.3 红娘联系方式展示规则

后端可以提供现有接口：

```http
GET /api/v1/matchmaker/service-requests/{service_id}/contact
```

满足以下条件时返回红娘微信：

- Token 有效。
- 当前用户是该服务申请的所属用户。
- 对应订单已支付成功。
- 服务未退款、未取消、未被风控隐藏。
- 红娘已提交联系方式。

接口不返回无关用户的手机号、微信号或内部 ID。父母端是否显示微信按钮、电话按钮以及具体展示样式由父母端前端决定，但前端不能绕过后端接口自行拼接或使用缓存展示联系方式。

### 5.4 父母端电话的处理

父母端 XMind 写有电话按钮，但当前后端安全规则要求联系方式授权。建议采用：

```text
父母端发起联系方式交换申请
-> 红娘或目标用户收到通知
-> 对方明确同意
-> 状态进入双方同意/已交付
-> 父母端调用联系方式查询接口
-> 后端返回经过授权的手机号
```

若产品最终决定父母端可直接查看“红娘电话”，也只能限定为红娘联系方式，不能扩展为查看其他用户电话，并且必须：

- 明确父母账号与服务订单的归属关系。
- 记录查看行为审计日志。
- 退款、拉黑、封禁、注销或风控后停止展示。
- 不在列表接口、推荐接口和公开红娘详情接口中返回电话。

### 5.5 父母端接口响应建议

红娘服务详情可以统一返回以下非敏感字段：

```json
{
  "id": 31,
  "user_id": 23,
  "matchmaker_id": 12,
  "service_type": 1,
  "order_id": 31,
  "status": 1,
  "contact_available": true,
  "contact_viewable": true,
  "contact_hidden_reason": null,
  "created_at": "2026-08-03T10:00:00Z",
  "updated_at": "2026-08-03T10:30:00Z"
}
```

只有调用专门的联系方式接口时才返回联系方式内容。列表和详情接口只返回 `contact_available`、`contact_viewable` 等状态字段。

### 5.6 父母端前端工作流

```text
红娘列表
-> 红娘详情
-> 选择商品和填写需求
-> 创建订单
-> 支付
-> 订单状态轮询/回调刷新
-> 服务申请详情
-> “查看联系方式”按钮
-> 后端鉴权成功后显示联系方式
```

前端需要处理：

- 未实名：跳转认证页。
- 未支付：显示待支付，不显示联系方式。
- 红娘未提交联系方式：显示等待红娘提交。
- 联系方式已隐藏：显示服务暂不可用，不展示隐藏原因中的敏感信息。
- 非订单所属人：显示无权查看。
- 订单退款或服务取消：清理本地联系方式缓存。

## 6. 双重认证和统一门禁

双重认证定义为：

```text
实名认证 = 姓名 + 身份证信息校验
人脸识别认证 = 人脸识别结果通过
双重认证 = 实名认证通过 AND 人脸识别认证通过
```

建议认证状态拆开保存：

- `realname_status`
- `face_status`
- `double_verified` 仅作为计算结果，不作为唯一事实来源

一期如果真实人脸供应商尚未接入，只能使用认证状态机、供应商适配层和测试 Mock；生产环境不能把 Mock 结果当作真实双重认证结论。

功能门禁建议：

| 功能 | 一期要求 |
| --- | --- |
| 浏览公开红娘和社区内容 | 登录后，受账号状态和隐私过滤影响 |
| 发布帖子、评论、点赞、关注 | 双重认证通过，且没有对应功能限制 |
| 申请认识 | 双重认证通过，且有可用额度 |
| 普通聊天 | 双方匹配成功，且双方没有私信限制 |
| 发送纸飞机 | 双重认证通过，且没有纸飞机限制和额度不足 |
| 创建红娘服务订单 | 双重认证通过、账号正常、订单金额有效 |
| 申请成为红娘 | 双重认证通过，提交资料后人工审核 |
| 查看红娘联系方式 | 服务订单归属本人、支付成功、授权和状态有效 |

## 7. 聊天撤回双接口方案

### 7.1 保留的两个接口

```http
DELETE /api/v1/chat/messages/{message_id}
POST   /api/v1/chat/messages/{message_id}/recall
```

两者必须调用同一个服务层方法，不能分别实现不同的撤回规则。

### 7.2 统一撤回规则

- 只能撤回自己发送的消息。
- 只允许在产品规定的时间窗内撤回，建议配置化，例如发送后 2 分钟内。
- 消息已经被管理员屏蔽、已被系统删除或超过时间窗时返回明确错误。
- 撤回后保留消息记录和必要审计信息。
- 普通用户历史消息只返回撤回占位文本，例如“消息已撤回”。
- 管理员在举报或治理场景可按权限查看原文，并写入审计日志。
- 重复撤回应幂等返回已撤回结果，不重复写操作记录。

### 7.3 统一响应示例

```json
{
  "id": 101,
  "session_id": 8,
  "sender_id": 23,
  "type": 1,
  "content": "消息已撤回",
  "media_url": null,
  "is_recalled": true,
  "recalled_at": "2026-08-03T10:02:00Z",
  "created_at": "2026-08-03T10:00:00Z"
}
```

前端可以根据客户端版本调用任一接口，但必须使用同一响应字段处理结果。

## 8. 红娘一期规则调整

### 8.1 产品范围

一期只保留：

- 付费牵线
- 私人定制商品的基础订单/服务框架
- 服务红娘申请、审核和展示
- 服务申请分配和处理
- 红娘微信交付
- 联系方式双方授权

一期不提供：

- 免费红娘服务次数
- 会员不限次数牵线
- 积分兑换红娘服务
- AI 红娘
- 真实支付回调前的生产开通
- 佣金、分账和提现

### 8.2 订单到联系方式流程

```text
查询上架商品
-> 创建订单并提交 Idempotency-Key
-> 调起真实支付
-> 支付回调验签并幂等更新订单
-> 创建服务申请
-> 通知服务红娘
-> 红娘接单并处理
-> 红娘提交微信
-> 订单所属用户查看微信
```

退款、取消、拉黑、封禁和注销都必须触发联系方式隐藏，并保留历史授权和审计记录。

## 9. 实施阶段与测试流程

### 阶段一：冻结数据和规则

1. 冻结双重认证字段及状态机。
2. 冻结举报原因、审核结论、处置动作映射。
3. 冻结总封禁和单项限制的可见性矩阵。
4. 冻结父母端账号、订单归属和联系方式授权规则。
5. 在 XMind 和接口文档中标注一期、二期和已废弃能力。

### 阶段二：公共安全能力

1. 统一用户状态和功能限制依赖。
2. 统一实名/人脸/双重认证门禁。
3. 统一拉黑和封禁过滤。
4. 统一举报、审核、处置、申诉和审计模型。
5. 统一通知写入和治理结果必达规则。

### 阶段三：红娘改造

1. 清理免费服务类型和免费次数入口。
2. 保留付费牵线和私人定制服务类型。
3. 完善支付回调、退款、服务开通幂等。
4. 完善红娘资格暂停、恢复和下架接口。
5. 完善父母端复用接口的订单归属和联系方式授权。
6. 增加服务完成评价和排行榜统计口径说明。

### 阶段四：社区和消息治理

1. 补齐消息举报目标类型和后台聊天证据接口。
2. 补齐总封禁后的公开数据过滤。
3. 增加聊天撤回双接口并统一服务层逻辑。
4. 增加消息发送幂等和媒体审核状态。
5. 清理社区 API 文档中的历史冲突描述。

### 阶段五：测试验收

必须覆盖：

- 未实名、仅实名、双重认证通过三种门禁状态。
- 普通用户、父母账号、服务红娘、超级管理员越权访问。
- 重复举报、并发举报、重复审核和终态改判。
- 总封禁前后主页、帖子、评论、头像、案例和聊天的可见性。
- 解封后内容恢复规则。
- 红娘订单重复创建、重复回调、退款后联系方式隐藏。
- 父母端非订单所有人访问联系方式。
- `DELETE` 和 `POST /recall` 撤回结果一致。
- 撤回超时、重复撤回、管理员查看原文和审计。
- 拉黑、限制私信、限制申请认识和总封禁的组合场景。

## 11. 最终验收标准

- 一期不存在免费红娘服务次数入口。
- 会员不限次数牵线不在一期生效，后续变更可配置并可追溯。
- 双重认证明确由实名和人脸识别组成。
- 举报全部进入人工审核，审核和处置可追溯。
- 总封禁不删除数据，但普通用户端和父母端不展示相关内容。
- 父母端复用同一后端，联系方式由后端按订单和授权控制，前端仅决定是否展示入口。
- 两个聊天撤回接口行为一致，消息原文和撤回记录按权限留存。
- 社区、消息、红娘后台治理有统一审计日志。
- 所有接口具有明确 Schema、权限、错误码、分页、幂等和状态流转文档。
