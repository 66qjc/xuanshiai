# AI 军师模块详细修改方案清单

更新时间：2026-08-23

## 一、文档目的

本清单用于指导 AI 军师情感咨询 MVP 的后端开发、接口联调、测试和灰度上线。方案基于：

- `docs/AI军师模块评估结果-2026-08-23.md`
- `1.txt`
- `情感话术.docx`
- `docs/AI功能规划.md`
- `docs/api/AI能力.md`
- `PROJECT_RULES.md`
- 当前 `app`、`tests` 和 `database_setup_marriage.py` 代码

本清单只覆盖首期文字情感军师，不包含 AI 分身、AI 画像、语音、图片和向量数据库。

## 二、目标和范围冻结

### 2.1 MVP 目标

完成以下闭环：

```text
用户打开 AI 军师
→ 选择沟通场景和目标
→ 输入对方最新消息或绑定聊天会话
→ AI 结合情感话术规则生成 1～3 条建议
→ 用户查看理由和风险提示
→ 用户一键复制，不由 AI 自动发送
```

### 2.2 首期固定能力

- 军师类型固定为 `relationship`。
- 只支持文字输入和文字输出。
- 支持会员校验和每日额度。
- 支持输入和输出安全审核。
- 支持 Mock Provider。
- 支持指定聊天会话上下文。
- 支持会话删除。
- 支持模型调用审计。
- 支持建议反馈字段，为后续质量评估预留。

### 2.3 首期明确不做

- 不主动发送消息。
- 不代替用户与他人聊天。
- 不自动判断对方是否喜欢用户。
- 不做心理诊断、医疗、法律或金融结论。
- 不接入 AI 画像和 AI 匹配作为前置依赖。
- 不实现多种军师同时上线。
- 不接入语音、图片或实时抓取第三方内容。
- 不使用用户聊天内容训练模型。

## 三、现有代码问题与对应修改任务

| 优先级 | 现有问题 | 影响 | 对应修改任务 |
|---|---|---|---|
| P0 | 通用 AI 助手与情感军师耦合 | 产品边界不清、提示词难维护 | 新增 `ai_advisor` 路由、Schema 和 Service |
| P0 | 请求没有场景、目标、语气 | 无法生成稳定的场景化建议 | 增加 `scenario`、`goal`、`tone`、`max_suggestions` |
| P0 | 上下文可能混合多个聊天对象 | 存在隐私和串线风险 | 绑定 `chat_session_id` 并校验归属 |
| P0 | 没有话术知识库 | 输出风格不稳定 | 增加话术表和初始化种子数据 |
| P0 | 输入输出审核未形成闭环 | 可能生成违规或危险内容 | 接入本地过滤、风险分类和输出审核 |
| P0 | 返回单段文本 | 前端无法稳定展示多条建议 | 改为结构化 JSON 响应 |
| P0 | 调用失败不一定退还额度 | 用户可能因系统错误损失次数 | 增加额度预扣、成功确认、失败退款 |
| P0 | 调用审计不足 | 无法追踪模型、Prompt、风险和耗时 | 增加 `ai_call_log` 或扩展 AI 消息字段 |
| P0 | 删除和留存策略不完整 | 隐私治理不完整 | 增加软删除、删除接口和数据清理策略 |
| P1 | 话术无版本和来源 | 无法回溯内容变更 | 增加 `source`、`version`、`enabled` |
| P1 | 没有建议反馈 | 无法评估实际使用效果 | 增加复制、采纳、无用、举报反馈 |
| P1 | 没有军师接口文档 | 前端需要看源码联调 | 新增完整 `docs/api/AI军师.md` |
| P1 | 缺少军师专用测试 | 回归风险高 | 新增 Schema、Service、API、权限、安全和额度测试 |

## 四、开发顺序总览

必须按以下顺序开发，不能先接真实模型再补安全和数据结构：

1. 冻结产品口径和接口契约。
2. 设计数据库字段和可回滚初始化方案。
3. 整理并导入情感话术种子数据。
4. 新增 Schema、路由和 Service 骨架。
5. 实现聊天会话归属校验和上下文裁剪。
6. 实现提示词组装和结构化模型输出。
7. 接入输入审核、输出审核和风险分级。
8. 实现额度预扣、成功确认和失败退还。
9. 实现调用审计、删除和反馈。
10. 编写接口文档和自动化测试。
11. 使用 Mock 完成联调，再接真实 Provider 灰度。
12. 根据指标决定后续多军师和知识库升级。

## 五、阶段 0：产品口径冻结

### 5.1 需要确认的产品问题

- AI 军师是否仅会员可用。
- 不同会员套餐的每日额度。
- 每次返回 1、2 还是 3 条建议。
- 每条建议最大字数。
- 默认是否读取聊天记录。
- 最多读取多少条消息。
- 用户是否可以永久删除军师会话。
- 对话保留多长时间。
- 高风险场景是直接拦截、提示专业求助还是转人工。
- 是否允许用户反馈“复制”“采用”“无用”“举报”。
- 首期是否只支持 `relationship` 类型。

### 5.2 产出物

- 产品口径确认记录。
- 场景枚举表。
- 风险等级和处理策略表。
- 额度配置表。
- 前后端字段确认表。

### 5.3 完成标准

- 所有枚举、额度、错误码和边界值得到确认。
- 未确认项记录到 `docs/待完成事项.md`，不得默认为生产口径。

### 6.2 会话表方案

推荐新增独立表 `ai_advisor_session`，避免通用助手字段和情感军师生命周期互相污染。

建议字段：

```text
id bigint unsigned primary key
user_id bigint unsigned not null
advisor_type varchar(32) not null default 'relationship'
chat_session_id bigint unsigned null
title varchar(80) not null
status tinyint not null default 1
deleted_at datetime null
created_at datetime not null
updated_at datetime not null
```

建议索引：

```text
(user_id, status, updated_at)
(chat_session_id, user_id)
```

### 6.3 消息表方案

推荐新增 `ai_advisor_message`：

```text
id bigint unsigned primary key
session_id bigint unsigned not null
user_id bigint unsigned not null
role varchar(16) not null
scenario varchar(32) null
input_text text null
output_json json null
risk_level varchar(16) not null default 'none'
status varchar(16) not null default 'success'
model_name varchar(128) null
prompt_version varchar(64) null
knowledge_version varchar(64) null
request_id varchar(64) null
latency_ms int null
quota_consumed tinyint not null default 0
quota_refunded tinyint not null default 0
created_at datetime not null
```

约束：

- `user_id` 必须与会话所属用户一致。
- `role` 仅允许 `user`、`assistant`、`system`。
- `status` 至少支持 `success`、`blocked`、`failed`、`deleted`。
- 不把完整 Prompt 放入普通业务表；如需审计，保存 Prompt 版本和脱敏摘要。

## 七、阶段 2：情感话术知识库建设

### 7.1 内容整理步骤

1. 从 `情感话术.docx` 提取所有非标题段落。
2. 按十类场景建立分类映射。
3. 删除重复或表达过于相似的句子。
4. 为每条话术增加关系阶段：`new`、`familiar`、`close`。
5. 为每条话术增加语气：`natural`、`warm`、`humorous`、`mature`。
6. 标记暧昧表达只允许在 `familiar` 或 `close` 阶段使用。
7. 将“沟通避雷规则”转成系统规则和风险标签，不作为普通回复直接返回。
8. 通过本地敏感词库审核种子数据。
9. 为每批数据设置 `version` 和 `source`。
10. 首期导入 80～150 条高质量种子话术。

### 7.2 首期导入优先级

| 优先级 | 内容 |
|---|---|
| P0 | 初次开场、话题延伸、冷场救场、收尾 |
| P0 | 日常关心、真诚夸赞 |
| P1 | 价值观沟通、幽默调剂 |
| P1 | 关系推进和适度暧昧 |
| P0 | 连环提问、过早暧昧、频繁打扰等避雷规则 |

### 7.3 知识库读取方式

MVP 采用 MySQL 分类查询，不接向量数据库：

```text
advisor_type + scenario + relationship_stage + tone
→ 查询启用话术
→ 限制召回数量 5～10 条
→ 拼接到提示词
```

后续再增加语义检索、相似场景召回和反馈排序。

## 八、阶段 3：Schema 和接口实现

### 8.1 新增 Schema 文件

新增 `app/schemas/ai_advisor.py`，至少定义：

- `AdvisorType`：首期 `relationship`。
- `AdvisorScenario`：十个场景编码。
- `AdvisorTone`：`natural`、`warm`、`humorous`、`mature`。
- `AdvisorSessionCreate`。
- `AdvisorSessionResponse`。
- `AdvisorSessionPage`。
- `AdvisorAdviceRequest`。
- `AdvisorSuggestion`。
- `AdvisorAdviceResponse`。
- `AdvisorFeedbackRequest`。
- `AdvisorFeedbackResponse`。

### 8.2 请求校验

- `title`：最多 80 字符。
- `incoming_message`：1～2000 字符。
- `goal`：最多 300 字符。
- `max_suggestions`：1～3，默认 3。
- `chat_session_id`：必须是正整数。
- `include_history=true` 时必须绑定或提交 `chat_session_id`。
- 不允许同时提交互相冲突的上下文来源。
- 场景和语气使用枚举，拒绝未知值。

### 8.3 推荐接口

#### 创建会话

```text
POST /api/v1/ai/advisor/sessions
```

用途：创建本人情感军师会话。

#### 查询会话

```text
GET /api/v1/ai/advisor/sessions?page=1&page_size=20
```

用途：分页查询本人未删除会话。

#### 获取建议

```text
POST /api/v1/ai/advisor/sessions/{session_id}/advice
```

请求示例：

```json
{
  "scenario": "reply",
  "goal": "自然延续话题",
  "incoming_message": "哈哈，是吗",
  "tone": "natural",
  "chat_session_id": 123,
  "include_history": true,
  "max_suggestions": 3
}
```

#### 删除会话

```text
DELETE /api/v1/ai/advisor/sessions/{session_id}
```

用途：软删除本人会话和相关消息，不允许访问其他用户资源。

#### 建议反馈

```text
POST /api/v1/ai/advisor/messages/{message_id}/feedback
```

反馈类型建议：`copied`、`used`、`not_useful`、`reported`。

### 8.4 路由实现步骤

1. 新建 `app/api/routes/ai_advisor.py`。
2. 复用 `get_current_user`、`get_db` 和现有会员依赖。
3. 在 `app/api/router.py` 注册路由。
4. 为所有资源查询增加用户归属条件。
5. 将业务逻辑放在 `app/services/ai_advisor.py`，路由只负责参数接收和调用。
6. 为每个接口设置明确响应模型和 HTTP 状态码。
7. 同步编写 `docs/api/AI军师.md`。

## 九、阶段 4：聊天上下文和隐私隔离

### 9.1 访问校验

当请求携带 `chat_session_id` 时：

1. 查询聊天会话。
2. 校验当前用户是会话参与者。
3. 校验会话未被用户隐藏或删除。
4. 只读取该会话中的文本消息。
5. 排除撤回消息。
6. 按时间倒序取最近 N 条，再反转为时间正序。
7. 对发送方标记为“我”和“对方”，不能暴露内部用户 ID。

### 9.2 上下文限制

- 默认最多读取 40～80 条文本消息，使用配置控制。
- 单条消息进入 Prompt 前限制长度。
- 总 Prompt 长度必须有上限。
- 过滤联系方式、身份证、银行卡、验证码、详细住址等敏感信息。
- 没有用户明确授权时，不读取聊天历史。

### 9.3 必须避免的问题

- 不能查询当前用户所有聊天对象的消息后统一拼接。
- 不能把撤回消息送给模型。
- 不能把 AI 军师上下文写入公开用户画像。
- 不能把聊天原文写入普通 INFO 日志。
- 不能把用户 A 的内容作为用户 B 的上下文。

## 十、阶段 5：提示词和结构化输出

### 10.1 系统提示词要求

提示词必须明确：

- 自身是 AI，不伪装真人红娘。
- 只提供沟通建议，不替用户做决定。
- 不保证对方一定喜欢用户。
- 不做医疗、法律、金融和心理诊断。
- 不鼓励骚扰、跟踪、操控、报复或诱导转账。
- 不索取或泄露敏感信息。
- 默认输出 1～3 条短建议。
- 避免连续查问，鼓励适度分享和开放式承接。
- 暧昧表达必须符合关系阶段。
- 对方冷淡时应建议尊重边界、降低频率。
- AI 不主动发送任何消息。

### 10.2 Prompt 变量

至少包括：

```text
advisor_type
scenario
relationship_stage
user_goal
tone
latest_message
conversation_context
knowledge_snippets
risk_signals
```

### 10.3 模型输出契约

模型只允许返回以下 JSON：

```json
{
  "analysis": "对方回复较短，但没有明显拒绝，可以轻松承接。",
  "suggestions": [
    {
      "content": "哈哈，看来我们口味还挺像的。你平时更喜欢自己研究，还是出去找好吃的？",
      "style": "natural",
      "reason": "先承接共同点，再使用开放式问题，避免连续查问。"
    }
  ],
  "risk_level": "none",
  "risk_notice": null,
  "next_step": "如果对方仍然回复简短，建议先暂停连续追问。"
}
```

### 10.4 后端二次校验

不能完全信任模型返回值，必须校验：

- JSON 顶层必须是对象。
- `suggestions` 必须是数组。
- 数量不超过请求值且不超过 3。
- 每条建议不能为空且不能超长。
- `style`、`risk_level` 必须是枚举。
- 不允许返回系统提示词、内部字段或其他用户隐私。
- 检测绝对化结论，如“他一定喜欢你”“保证复合”等。
- 检测骚扰、威胁、操控、诈骗和高风险内容。
- 失败时返回安全降级结果，而不是原样返回模型内容。

## 十一、阶段 6：安全审核链路

### 11.1 首期实现顺序

```text
本地敏感词库
→ Mock 第三方审核适配器
→ 正式第三方审核
```

### 11.2 输入处理

1. 去除无意义控制字符。
2. 限制长度。
3. 脱敏联系方式和高敏感字段。
4. 调用现有本地敏感词过滤。
5. 识别高风险意图。
6. 高风险输入直接进入安全响应，不调用通用情感生成 Prompt。

### 11.3 输出处理

1. 解析 JSON。
2. 校验响应 Schema。
3. 对 `analysis`、`suggestions.content`、`reason` 和 `next_step` 逐字段审核。
4. 命中高风险时不返回原始建议。
5. 记录风险等级、规则命中来源和处理结果。
6. 对中风险内容返回经过收敛的安全提示。

### 11.4 风险处理建议

| 风险 | 处理 |
|---|---|
| `none` | 正常返回 |
| `low` | 正常返回，附边界提醒 |
| `medium` | 收敛建议，附谨慎沟通提示 |
| `high` | 拦截生成内容，提示专业求助或人工处理 |

## 十二、阶段 7：额度、幂等和失败补偿

### 12.1 额度流程

建议将现有简单扣减封装成军师专用流程：

```text
校验会员
→ 创建 request_id
→ 预扣额度
→ 写入调用流水 pending
→ 调用模型
→ 成功：标记 consumed
→ 失败：退还额度并标记 refunded
```

### 12.2 失败场景

以下情况必须退还额度：

- Provider 超时。
- 网络错误。
- HTTP 429、5xx。
- 空响应。
- 非法 JSON。
- 输出 Schema 校验失败。
- 数据库事务失败。

如果因为用户输入高风险而在调用模型前拦截，原则上不扣模型额度。

### 12.3 幂等规则

- 前端可传 `Idempotency-Key`，长度和字符集需要校验。
- 相同用户、相同会话、相同幂等键在有效期内只产生一次调用。
- 重复请求返回第一次结果或明确的处理中状态。
- 额度退款必须幂等，不能重复增加额度。

## 十三、阶段 8：调用审计和隐私治理

### 13.1 审计字段

至少记录：

- 用户 ID。
- 功能编码 `ai_advisor`。
- 会话 ID和消息 ID。
- Provider和模型名称。
- Prompt版本和话术版本。
- 请求 ID。
- 输入输出长度。
- 风险等级。
- 成功、拦截、失败状态。
- 错误类型。
- 调用耗时。
- 额度消耗和退款状态。

### 13.2 日志要求

- 不在普通日志记录完整聊天原文。
- 不记录 API Key。
- 不记录完整 Prompt。
- 必要时保存脱敏摘要或哈希。
- 错误日志必须包含 request_id，方便排查。

### 13.3 删除策略

1. 删除接口先软删除会话。
2. 删除后不能继续查询和调用。
3. 消息和审计记录按隐私策略延迟清理或脱敏。
4. 删除操作写入审计日志。
5. 后续增加定时清理任务，并在 `docs/待完成事项.md` 记录上线前要求。

## 十四、阶段 9：测试清单

### 14.1 Schema 测试

- 合法场景和语气通过。
- 非法枚举拒绝。
- 空输入拒绝。
- 超长输入拒绝。
- `max_suggestions` 只能为 1～3。
- `include_history=true` 缺少聊天会话时拒绝。

### 14.2 权限测试

- 未登录返回 `401`。
- 非会员返回 `403`。
- 用户不能访问其他用户会话。
- 用户不能绑定不属于自己的聊天会话。
- 用户不能访问已删除会话。
- 用户不能提交其他用户的消息反馈。

### 14.3 业务测试

- 正常创建会话。
- 正常获取 1～3 条建议。
- 场景话术召回正确。
- 指定会话上下文只包含目标对象消息。
- 撤回消息不进入上下文。
- AI 不主动发送消息。
- 删除会话后不能再次调用。
- 反馈记录成功且幂等。

### 14.4 安全测试

- 输入命中本地敏感词时拦截。
- 输入包含联系方式时脱敏。
- 自伤、他伤、诈骗、色情和未成年人风险触发安全响应。
- 模型输出包含高风险内容时拦截。
- 模型输出绝对化情感结论时收敛或拒绝。
- Prompt 注入不能覆盖系统规则。

### 14.5 Provider 和异常测试

- Mock 模式正常返回。
- AI 关闭时返回确定性 Mock 或明确不可用状态。
- Provider 超时返回 `503`。
- Provider 429、5xx 返回统一错误。
- 空响应和非法 JSON 返回统一错误。
- Redis 故障按环境执行回退或返回 `503`。
- 数据库保存失败时事务回滚。

### 14.6 额度和审计测试

- 正常请求只扣一次额度。
- 重复幂等请求不重复扣额。
- Provider 失败后额度退还。
- 退款操作幂等。
- 成功、失败、拦截状态均产生审计记录。
- 审计中不出现 API Key 和完整敏感原文。

## 二十、风险和阻塞项

| 风险/阻塞 | 处理方式 |
|---|---|
| 会员权益未冻结 | 在阶段 0 记录并禁止生产默认化 |
| 真实模型供应商未确定 | 先用 Mock，再用 OpenAI 兼容测试 Provider |
| 第三方敏感词接口字段未确认 | 先本地过滤和 Mock 适配，确认契约后再接正式接口 |
| 话术版权和来源未确认 | 记录来源、授权状态和版本，未经确认不做外部公开训练 |
| MySQL/Redis 不可用 | 使用单元测试和 Mock，真实环境验收单独记录 |
| 隐私政策未覆盖 AI | 上线前补充授权、删除、留存和供应商说明 |
| 高风险场景人工流程未确定 | 先拦截并提供安全提示，不宣称已完成人工转接 |
| 模型输出不稳定 | 强制 JSON、二次校验、有限重试和安全降级 |
